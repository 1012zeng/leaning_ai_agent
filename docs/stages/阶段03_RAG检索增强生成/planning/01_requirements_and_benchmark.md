## 3. 能力差距分析：从"能读简单 Python"到"独立交付 RAG"

### 3.1 入口能力画像（Entry Profile）

| 维度 | 入口水平 |
|---|---|
| 编程 | 能读简单 Python：函数、类、`requests`/`json`/`os`、列表推导；能读写文件 |
| LLM 概念 | 听过"Prompt""幻觉""向量"等术语，能使用 ChatGPT 类工具，但未调用过 API |
| 工程 | 用过 `pip install`，未用过配置管理、日志、模块化项目结构 |
| 数学 | 高中数学水平；未将点积/余弦相似度与"语义相似"建立联系 |

### 3.2 出口能力画像（Exit Profile）

学员在阶段结束时**应能独立**完成以下可观察行为（非"知道"而是"做到"）：

1. **解释**：画出 RAG 完整数据流，标注每个节点的数据对象类型/形状/字段，能向非技术听众说清"为什么需要 RAG 而不是微调"
2. **追踪**：沿 `source_document_id → source_version_id → chunk_id → embedding_id → ranked_hit_id → citation_id` 追踪一条真实数据，说出每个环节的不变量
3. **调试**：给定一个"回答质量差"的 RAG 系统，能在 30 分钟内定位是检索问题还是生成问题，并给出可验证的修复方案
4. **评测**：为一个新数据集设计评估方案，选指标、建真值集、跑消融实验、写报告
5. **交付**：从零搭建一个可配置、可复现、可观测的 RAG 项目，代码结构达到模块化工程标准

### 3.3 差距分解（Gap Breakdown）

| # | 差距 | 从（入口） | 到（出口） | 对应需求域 |
|---|---|---|---|---|
| G1 | 概念建模 | 没听过 RAG | 能解释三大范式（Naive/Advanced/Modular）及选型依据 | D1 概念与范式 |
| G2 | 数据工程 | 不会处理 PDF/HTML/MD | 能按文档类型选加载器、设计分块策略、处理元数据 | D2 数据工程 |
| G3 | 向量化 | 不懂 embedding | 能选型 embedding 模型、构建向量索引、解释索引类型对召回/延迟的影响 | D3 向量化与索引 |
| G4 | 检索优化 | 只会向量相似度搜索 | 能实现混合检索、查询改写、路由、Rerank，并解释每步对指标的影响 | D4 检索优化 |
| G5 | 生成集成 | 直接拼 prompt | 能设计防幻觉 prompt、实现引用溯源、控制输出格式 | D5 生成集成 |
| G6 | 系统评估 | 凭感觉判断"好不好" | 能用 RAG Triad + 经典指标量化，设计消融实验，定位瓶颈 | D6 系统评估 |
| G7 | 工程交付 | notebook 式 demo | 模块化、配置化、可观测、可复现的项目工程 | D7 工程交付 |
| G8 | 故障定位 | 报错就慌/盲目重试 | 能按数据流定位到具体组件，复现故障，用指标解释根因 | D8 故障定位与调试 |

## 5. "代码级名词图谱"的可观察能力定义

> 用户否决的是"Chunk 是文本块、Milvus 是向量库"式定义。本节定义"代码级名词图谱"应让学员**做到**什么。

### 5.1 能力定义

对每个核心名词（Chunk、Embedding、Index、Query、RankedHit、Citation、Prompt、Context、Route、Rerank），学员应能：

| # | 可观察能力 | 判定方式 |
|---|---|---|
| N1 | **画出数据流图**：用真实字段名（如 `source_document_id`、`source_version_id`、`chunk_id`、可选 `parent_chunk_id`、`embedding_id`、`raw_score`、`final_score`）标注从“原始文档”到“最终引用”的完整链路 | 学员在白板/文档中画出并标注，字段名与 MUJI-19 契约及实现代码一致 |
| N2 | **沿调用链追踪一条数据**：给定一个 `source_document_id`，能在 C8 类项目中找到对应内容版本 → chunk → embedding → 一次检索中的 RankedHit → 最终 Citation | 实操：在调试器/打印中定位并说出每步数据形态 |
| N3 | **解释参数改变后的失败模式**：例如 `chunk_size` 从 256→2048，能预测 recall ↑ / precision ↓ / latency ↑，并用指标验证 | 设计并运行消融实验，输出对比表 |
| N4 | **复现并定位故障**：给定"检索返回无关块"现象，能定位是分块/embedding/index/查询哪一环，并给出修复 | 故障注入实验：人为制造故障 → 学员定位 → 修复 |
| N5 | **说出不变量**：每个环节的数据不变量（如 chunk 必有 `source_document_id/source_version_id`，仅层级分块时才有 `parent_chunk_id`；embedding 维度与 index manifest 一致；原始/融合/重排分数不可混用） | 口头/书面回答，与 MUJI-19 契约及代码一致 |
| N6 | **用指标验证假设**：能选用 Recall/MRR/Precision、忠实度、答案相关性等指标，解释"为什么改好了/改坏了" | 实验报告含指标对比与结论 |

### 5.2 名词图谱覆盖清单（与代码绑定）

| 名词 | 绑定的真实代码位置 | 绑定的数据对象/字段 |
|---|---|---|
| 参考仓库 Document / 目标 Chunk | `data_preparation.py` 的 `Document(page_content, metadata)` 仅作为待适配输入；跨模块使用 MUJI-19 的独立 `Chunk` DTO | `source_document_id`、`source_version_id`、`chunk_id`、可选 `parent_chunk_id`、`document_char_span`、`token_count`、`chunk_profile` |
| Embedding | `index_construction.py` BGE 调用 | `dense_vector` 维度、`ef.dim['dense']` |
| Index | Milvus `Collection` + FAISS `VectorStoreIndex` | `SPARSE_INVERTED_INDEX`, `AUTOINDEX`, `metric_type="IP"` |
| Query / Route | `generation_integration.py` `query_router` | `list` / `detail` / `general` |
| RankedHit | `retrieval_optimization.py` `hybrid_search` | `hit.distance`, `hit.entity.get('title')` |
| Citation / 引用溯源 | 生成模块的 context 拼接 | 来源文档标题 + 页码/章节 |
| Rerank | C4 `07_rerank_and_refine.py` | RRF `k=60`, `AnnSearchRequest` |
| Prompt | `generation_integration.py` 模板 | system prompt + context + question 拼接 |
| Context | 检索结果 → 父文档 → 去重排序 | `get_parent_documents` 按相关性计数排序 |

| 验收标准 | **正常**：给定一个 `source_document_id`，能在项目中追踪到 source version→chunk→embedding→RankedHit→Citation，说出每步数据形态与不变量。**边界**：追踪在混合检索/查询改写/路由介入后仍能说清链路变化。**错误**：当追踪断裂时（如 citation 指向错误文档），能定位到检索或去重环节。**恢复**：修复链路并验证。 |

## 7. 五维度能力分级

> 规则：每个维度分 L0–L4 五级，描述为可观察行为。用于章节验收、实验评分、出师考试命题。

### 7.1 代码阅读（Code Reading）

| 等级 | 可观察行为 | 判定方式 |
|---|---|---|
| L0 识别 | 能区分 Python 文件中的 import/函数/类/注释 | 指出一段代码的结构 |
| L1 读懂 | 能逐行解释教学示例（如 C2 `01_unstructured_example.py`）的输入/输出/作用 | 口头/书面解释 |
| L2 追踪 | 能沿调用链追踪一个数据对象从入口到输出（如 `partition()` → `elements` → `Counter` → 打印） | 在代码中标注数据流 |
| L3 映射 | 能将文档中的概念（如"父子分块"）映射到代码中的具体实现（`parent_child_map`、`get_parent_documents`） | 概念→代码双向标注 |
| L4 审辨 | 能发现示例代码中的设计缺陷或改进点（如硬编码路径、缺少错误处理）并提出重构方案 | 代码评审报告 |

### 7.2 代码修改（Code Modification）

| 等级 | 可观察行为 | 判定方式 |
|---|---|---|
| L0 运行 | 能跑通现有示例，得到预期输出 | 运行截图/日志 |
| L1 改参 | 能修改参数（如 `chunk_size`、`top_k`、`window_size`）并观察输出变化 | 改参前后对比 |
| L2 换件 | 能替换组件（如 FAISS→Milvus、BGE→另一 embedding）并保持系统运行 | 替换后跑通 |
| L3 新增 | 能新增模块（如给 C8 加 Rerank、加评估）而不破坏现有功能 | 新增模块跑通 + 原有测试通过 |
| L4 重构 | 能将 notebook 式代码重构为模块化工程（配置化、分离关注点） | 重构前后对比 + 可读性提升证据 |

### 7.3 故障定位（Fault Localization）

| 等级 | 可观察行为 | 判定方式 |
|---|---|---|
| L0 识别 | 能识别"系统不正常"（回答无关/报错/空结果） | 观察现象 |
| L1 分类 | 能判断是检索问题还是生成问题 | 看 TopK 结果即可判断 |
| L2 定位 | 能定位到具体组件（分块/embedding/index/query/prompt） | 用排除法+指标 |
| L3 根因 | 能说出根因机制（如"分块过大导致检索噪声，Recall 高但 Precision 低，LLM 被无关信息干扰"） | 含指标证据的解释 |
| L4 修复验证 | 能修复并用指标证明改善，且未引入新问题 | 修复前后对比 + 回归检查 |

### 7.4 实验设计（Experiment Design）

| 等级 | 可观察行为 | 判定方式 |
|---|---|---|
| L0 复现 | 能复现教程中的实验，得到相似结果 | 结果对比 |
| L1 单变量 | 能设计单变量实验（只改一个参数，其他固定） | 实验方案 |
| L2 消融 | 能设计消融实验（逐项移除/加入组件，观察指标变化） | 消融对比表 |
| L3 多指标 | 能选用 ≥2 类指标（检索+生成/忠实度+延迟）并解释权衡 | 多指标报告 |
| L4 决策 | 能根据实验结论做工程决策并辩护（如"因延迟约束，放弃 Rerank，改用更大 top_k"） | 决策报告含论据 |

### 7.5 工程交付（Engineering Delivery）

| 等级 | 可观察行为 | 判定方式 |
|---|---|---|
| L0 Demo | 能在自己环境跑通一个可交互的 RAG demo | 运行截图 |
| L1 可复现 | 项目含 `requirements.txt`、README，他人可复现 | 他人复现 |
| L2 模块化 | 数据/索引/检索/生成分离，配置集中管理 | 代码结构审查 |
| L3 可观测 | 含日志、指标输出、错误处理 | 运行日志 |
| L4 可交付 | 含评估集成、CI/测试、清理重建脚本，达到可展示标准 | 项目评审 |

## 附录 A：术语表

| 术语 | 定义（代码级） |
|---|---|
| Chunk | MUJI-19 定义的独立、不可变 DTO；必含 `chunk_id`/`source_document_id`/`source_version_id`/`document_char_span`，`parent_chunk_id` 仅在层级分块时出现；LangChain `Document` 只能停留在 adapter 内 |
| EmbeddingRecord | `embedding_id` 将 `chunk_id` 与 `embedding_profile` 绑定；`dimension` 必须等于向量长度和目标 IndexManifest 的 dimension，不能把某个 BGE 型号的维度写死为通用事实 |
| IndexManifest | 不可变索引构建清单，固定 `index_id`、corpus/profile、dimension、distance metric、coverage、checksum 与发布状态；Milvus/FAISS 对象只存在于 adapter 内 |
| RankedHit | 融合/重排后的不可变命中对象，含 `ranked_hit_id`、`candidate_ids`、`final_score`、`score_components`、`rerank_profile` 与 `eligible_for_context` |
| Citation | 事实 claim 到冻结 chunk 的可校验引用，至少绑定 `citation_id`、`claim_ids[]`、`chunk_id`、`source_version_id`、`quote` 与 `chunk_char_span` |
| Rerank | 对检索结果二次排序，常用 RRF 融合或交叉编码器 |
| Route | 按查询类型（list/detail/general）分发到不同检索/生成策略 |
| 父子分块 | 小块检索（精确）+ 大块生成（完整上下文）；仅此 profile 的子 Chunk 使用可选 `parent_chunk_id` 关联父 Chunk |
| RAG Triad | 评估三维度：上下文相关性 / 忠实度 / 答案相关性 |
| 消融实验 | 逐项移除/加入组件以观察指标变化的实验方法 |
