# 项目通用工程准则

版本：1.0  
适用范围：新建项目的默认工程基线；已有项目优先保持已批准且一致的本地约定  
关联规范：[多 Agent 软件研发组织与职责规范](./multi-agent-organization-standard.md)

## 1. 规范适用规则

1. 项目专属规范可以细化本准则，但不得降低安全、可测试性和职责分离要求。
2. 现有代码约定与本准则冲突时，由技术设计架构师记录 ADR 后选择统一方向，不允许新旧风格继续扩散。
3. 自动化检查应优先于人工记忆：能用格式化器、静态检查、Schema、测试或 CI 验证的规则必须自动化。
4. 示例是默认值，不是跨语言强制语法；具体语言规范由项目代码生成规范确定。

## 2. 文档准则

- 文档使用稳定编号：`REQ-`、`ADR-`、`API-`、`DB-`、`ERR-`、`AUTH-`、`MOD-`、`FUNC-`、`TEST-`、`REL-`。
- 文档必须记录版本、状态、责任人、审批人、依赖、变更原因和验证方式。
- 架构、接口、数据库、权限和错误码变更必须同步影响分析。
- 代码注释解释“为什么”和约束，不重复显而易见的代码行为。
- 复杂数据流、状态机和审批流使用可版本控制的 ASCII 或 Mermaid 图。
- 文档与实现不一致时，以已批准文档判定偏差；若实现代表新决定，先完成文档变更审批。

## 3. 代码命名准则

### 3.1 通用原则

- 标识符使用英文和 ASCII，业务展示文本按产品语言处理。
- 名称表达领域含义，避免 `data`、`info`、`temp`、`handle` 等无上下文名称。
- 同一概念全项目只使用一个术语；术语变化必须同步文档、接口、代码和测试。
- 布尔值使用 `is`、`has`、`can`、`should` 等可判断前缀。
- 集合使用复数；数量使用 `count`；时间点使用 `At`/`_at`；持续时长带单位，如 `timeoutMs`。
- 禁止自造缩写。通用缩写如 `id`、`url`、`api` 按语言惯例使用。

### 3.2 Python 默认

| 对象 | 规范 | 示例 |
|---|---|---|
| 包、模块 | `snake_case` | `order_service.py` |
| 函数、变量 | `snake_case` | `calculate_total` |
| 类、异常 | `PascalCase` | `OrderService` |
| 常量 | `UPPER_SNAKE_CASE` | `MAX_RETRY_COUNT` |
| 内部成员 | 前缀 `_` | `_load_config` |

### 3.3 TypeScript/JavaScript 默认

| 对象 | 规范 | 示例 |
|---|---|---|
| 普通文件 | `kebab-case` | `order-service.ts` |
| React组件文件 | `PascalCase` | `OrderSummary.tsx` |
| 函数、变量 | `camelCase` | `calculateTotal` |
| 类、类型、接口、组件 | `PascalCase` | `OrderService` |
| 全局常量 | `UPPER_SNAKE_CASE` | `MAX_RETRY_COUNT` |

接口不使用无意义 `I` 前缀；实现类不使用 `Impl`，应以职责区分，如 `SqlOrderRepository`。

### 3.4 测试命名

测试名表达“条件、动作、结果”，例如：

```text
given_expired_token_when_refresh_then_returns_auth_error
returnsPermissionErrorWhenApproverIsMissing
```

## 4. 目录与模块准则

- 模块按领域或业务能力划分，不按“所有控制器”“所有工具函数”形成全局杂物目录。
- 模块公开接口最小化；内部实现不被其他模块直接引用。
- 公共方法只有在至少两个稳定场景共享同一语义时才提取。
- `utils`、`helpers`、`common` 目录必须有清晰分类和责任人，禁止成为无边界堆放区。
- 模块之间通过批准的接口、事件或契约协作，不跨模块读写内部表和内部状态。

## 5. 数据库准则

- 表、字段、索引和约束使用 `snake_case`。
- 新项目默认表名使用复数，主键为 `id`，外键为 `<entity>_id`。
- 审计时间统一为 `created_at`、`updated_at`；软删除仅在业务需要时使用 `deleted_at`。
- 金额使用定点小数或最小货币单位整数，不使用浮点数。
- 时间在存储和接口层使用 UTC，展示层再转换时区。
- 关键业务约束同时落在应用校验和数据库约束；唯一性不能只靠查询后判断。
- 所有结构变更通过可审查迁移完成。迁移必须包含兼容策略、数据处理、验证和回滚方案。
- 破坏性迁移采用“扩展、迁移、切换、清理”分阶段执行，不与依赖旧结构的代码同时删除。
- 索引命名：`idx_<table>__<columns>`；唯一约束：`uq_<table>__<columns>`；外键：`fk_<table>__<target>`。

## 6. 接口设计准则

- 接口先定义契约，再实现客户端和服务端；契约包含类型、必填、默认值、约束和错误。
- REST 路径使用复数资源和 `kebab-case`，不在路径中使用动词代替资源语义。
- 同一项目的 JSON 字段风格必须统一；新项目默认公开 JSON 使用 `camelCase`，数据库保持 `snake_case`，在边界显式映射。
- 所有写操作明确幂等策略；创建、支付、审批、任务提交等高风险操作支持幂等键或业务唯一键。
- 列表接口明确分页、排序、筛选和最大页大小；禁止无上限返回。
- 时间使用 ISO 8601 UTC，例如 `2026-08-20T08:00:00Z`。
- 金额在接口中使用定点字符串或最小货币单位，并明确币种。
- 公共接口使用版本和兼容策略。新增可选字段通常向后兼容；删除、改名和语义变化必须升级版本或分阶段迁移。
- 请求和响应必须有 Schema，并在 CI 中执行契约校验。

## 7. 错误码规范

### 7.1 格式

业务错误码使用稳定格式：

```text
<DOMAIN>-<CATEGORY>-<NNNN>
```

示例：`ORD-VAL-0001`。推荐分类：

| 分类 | 含义 |
|---|---|
| `VAL` | 输入或业务校验失败 |
| `AUTH` | 身份认证失败 |
| `PERM` | 权限不足或审批条件不满足 |
| `NF` | 资源不存在 |
| `CONFLICT` | 状态、版本或唯一性冲突 |
| `RATE` | 频率或配额限制 |
| `EXT` | 外部服务失败 |
| `SYS` | 内部系统错误 |

错误码一经发布不得复用或改变语义。废弃码保留登记记录并标记 `DEPRECATED`。

### 7.2 错误响应

```json
{
  "success": false,
  "error": {
    "code": "ORD-VAL-0001",
    "message": "订单数量超出允许范围",
    "details": {},
    "requestId": "request-id-placeholder",
    "retryable": false
  }
}
```

- HTTP 状态表达协议结果，业务错误码表达稳定业务语义，两者不能互相替代。
- `message` 面向用户或调用方；日志通过 `requestId` 关联内部诊断信息。
- 响应不返回堆栈、SQL、凭据、内部路径或敏感数据。
- `retryable` 必须基于明确恢复策略，不能对业务校验错误标记可重试。
- 错误码登记表记录：代码、领域、触发条件、HTTP 状态、用户信息、是否重试、责任模块、引入版本和测试用例。

## 8. 权限与审批准则

- 默认拒绝，按最小权限授权；前端隐藏按钮不能代替服务端鉴权。
- 权限模型明确主体、资源、动作、范围和条件，形成可测试权限矩阵。
- 审批流使用显式状态机，定义每个状态、允许迁移、操作者和失败结果。
- 高风险流程默认分离提交人与批准人；需要例外时必须记录理由和审计事件。
- 每次权限或审批决定记录操作者、主体、动作、资源、决策、原因、时间和关联请求。
- 审计日志仅追加、限制访问并定义保留周期；敏感字段脱敏。
- 权限、审批、支付、删除和数据导出必须包含越权、重复提交、并发、过期和重放测试。

## 9. 自动化测试准则

- 测试从需求、架构、接口和风险推导，不从实现细节单向反推。
- 每条可验收需求至少映射一个自动化测试或明确的人工验收证据。
- 每个变更覆盖正常、边界、错误、恢复和既有行为回归路径。
- 纯函数和模块分支使用单元测试；跨服务契约使用契约/集成测试；关键用户流程使用 E2E；AI 行为使用离线评测。
- 缺陷修复先增加能稳定复现问题的回归测试，再修改实现。
- 测试可重复、隔离、可并行；不依赖执行顺序、真实生产数据或不可控外部服务。
- 覆盖率是发现缺口的指标，不是完成证明。项目可设置最低阈值，但关键路径必须按行为逐项验证。
- 测试报告至少包含执行环境、版本、用例范围、通过/失败/跳过、失败证据和未覆盖风险。

## 10. 公共组件和方法清单

公共资产登记至少包含：名称、类型、用途、责任人、位置、稳定性、输入输出、使用示例、依赖、兼容性和废弃计划。

新增公共资产前必须：

1. 检索现有目录并证明没有满足相同语义的组件。
2. 确认至少两个稳定复用场景，或属于必须统一的横切能力。
3. 定义清晰接口、错误行为和测试。
4. 指定责任人和版本策略。

不满足条件的逻辑保留在业务模块内部，避免过早抽象。

## 11. 日志、监控与隐私准则

- 日志使用结构化字段，至少包含时间、级别、服务、事件、请求标识和结果。
- 日志记录业务事件和失败上下文，不记录密码、Token、完整凭据、隐私数据或原始敏感响应。
- 关键路径定义指标、告警条件和责任人；健康检查必须区分进程存活与业务可用。
- 跨服务调用传播请求标识或 Trace 上下文。
- 告警必须可行动，包含影响、证据和运行手册入口。

## 12. 代码审查准则

- 作者不能批准自己的变更；审查人必须能够读取对应需求、设计和规范。
- 审查顺序：需求符合性 -> 架构和边界 -> 正确性 -> 数据与权限 -> 错误处理 -> 测试 -> 可维护性 -> 性能和运行影响。
- 问题分为：阻断、应修复、建议、疑问。每项包含位置、影响、证据和建议。
- 前端、数据库/API、权限审批等专项范围必须调用对应审查 Skill。
- 审查通过不替代自动化测试和运行验证。

## 13. CI/CD 与发布准则

合并前至少执行：格式化、静态检查、类型检查、单元测试、契约测试、构建和密钥扫描。按项目风险增加集成、E2E、安全、性能和迁移测试。

每次发布必须具备：

- 唯一版本和可追踪变更集
- 环境和配置差异检查
- 数据库迁移顺序及验证
- 发布前备份或恢复条件
- 灰度或分阶段发布策略
- 业务健康检查和监控
- 可执行回滚方案
- 发布记录和验收证据

HTTP 200、端口可连接或进程存活不能单独证明业务可用；关键流程必须执行真实业务级 canary 验证。

## 14. Definition of Ready

任务进入开发前必须满足：目标清晰、需求和设计已批准、接口稳定、依赖明确、允许修改范围确定、验收标准可测试、审查人和测试人已指定、风险和验证命令已记录。

## 15. Definition of Done

任务完成必须满足：实现符合批准文档、文档同步、代码经独立审查、自动化测试通过、错误与恢复路径验证、无未声明兼容风险、交付证据完整、下一责任人可以在无口头背景下继续工作。
