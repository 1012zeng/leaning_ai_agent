# 多 Agent 软件研发组织与职责规范

版本：1.0  
适用范围：采用 AI Agent 协作的软件项目  
规范级别：项目治理基线

## 1. 目的

本规范把 Agent 视为虚拟员工，把 Skill 视为员工掌握的标准作业能力。目标不是让一个 Agent 从需求做到发布，而是通过岗位分工、文档基线、职责分离和质量门禁，让每项交付都可追踪、可审查、可验证、可恢复。

## 2. 基本原则

1. **文档先行**：批准后的文档是设计和实现的唯一事实来源。
2. **动态组队**：九类岗位构成员工库；项目经理按复杂度选择参与岗位和 Agent 实例数。
3. **职责分离**：同一 Agent 不得同时担任同一交付物的作者和批准人。
4. **边界清晰**：每个任务必须限定目标、输入、允许修改范围、输出和验收条件。
5. **证据放行**：完成声明必须附带文档、代码、测试或运行结果，口头结论不能通过门禁。
6. **受控变更**：需求、架构和规范先变更文档，再同步 Skill，最后修改实现。
7. **最少充分团队**：只启用交付所需岗位，但不通过合并职责破坏独立审查。

## 3. 文档权威与构建顺序

文档的重要性与生成顺序不是同一概念。需求基线必须先形成，架构和全局规范则拥有更高的设计约束权。

### 3.1 权威等级

| 等级 | 文档 |
|---|---|
| L0 | 架构设计文档 |
| L1 | 前后端代码生成规范、数据库和接口设计规范 |
| L2 | 错误码规范、自动化测试规范、公共组件和方法清单 |
| L3 | 审批和权限设计规定 |
| L4 | 项目需求文档和验收标准 |
| L5 | 分模块详细设计 |
| L6 | 功能开发详细设计和任务说明 |

下级文档不得静默覆盖上级文档。该等级表示技术约束的影响范围，不授权架构文档改变已批准的业务目标。跨层冲突必须停止相关任务，由需求和技术责任人共同完成影响分析与变更审批。

### 3.2 项目构建顺序

```text
项目简报与需求基线
        -> 架构设计
        -> 全局工程规范与数据/接口契约
        -> 权限、审批、测试和公共资产规范
        -> 模块详细设计
        -> 功能详细设计与任务计划
        -> 项目 Skill
        -> 开发、审查、测试、发布和运行
```

每份受控文档至少包含：文档编号、版本、状态、责任人、审批人、上游依赖、下游消费者、变更记录、追踪编号和验证方式。状态统一为 `DRAFT -> REVIEW -> APPROVED -> BASELINED -> SUPERSEDED`。

## 4. 九类员工岗位

### 4.1 项目经理

负责初始化项目、评估复杂度、选择参与岗位和 Skill、拆解依赖任务、分配负责人/审查人/测试人、维护质量门禁并根据证据调整计划。项目经理不编写业务代码，不替专业岗位批准技术方案。

主要交付：

- 项目章程和范围基线
- 复杂度评估与人员配置计划
- WBS 工作分解、依赖图和里程碑
- Agent 任务分配清单、RACI 和风险登记表
- 质量门禁、状态报告和变更决策记录

### 4.2 产品与需求工程师

负责澄清业务目标、用户、场景、范围、业务规则和验收标准，维护需求到设计及测试的追踪关系。不得自行指定未经架构评估的技术实现。

主要 Skill：需求访谈、PRD 编写、用户故事、业务规则建模、验收标准、需求拆分、需求变更和追踪检查。

岗位配置和可执行 Skill 套件见[产品与需求工程师 Agent 配置](./product-requirements-engineer-agent-config.md)与[产品与需求工程师 Skill 套件](./product-requirements-engineer-skills/INDEX.md)。该岗位维护业务语义，架构可行性由技术设计架构师审查，可测试性由自动化测试工程师审查，项目级变更传播由项目经理组织。

### 4.3 技术设计架构师

负责技术栈、系统边界、模块划分、数据流、非功能需求、关键状态机和详细设计审批，维护架构决策记录。不得绕过需求批准扩大产品范围，也不得承担整个项目的实现。

主要 Skill：架构设计、ADR、模块设计、功能设计审查、依赖分析、性能/安全设计、模块功能审查和技术风险评估。

### 4.4 UI/UX 与前端规范工程师

负责用户流程、信息架构、交互状态、设计系统、前端生成规范、可访问性和前端公共组件目录。负责独立执行前端规范审查，不实现其本人需要批准的同一交付物。

主要 Skill：用户流程设计、线框与交互规范、设计系统、前端代码规范、组件复用审查、响应式与可访问性审查。

### 4.5 前端开发工程师

依据批准的需求、架构、接口契约和前端规范实现页面与组件，编写单元和组件测试，提交实现证据。不得自行修改公共接口、权限规则或设计系统基线。
主要 Skill：模块功能开发、前端实现、状态管理、接口适配、组件测试、性能检查和缺陷修复。

### 4.6 后端开发工程师

依据批准的模块设计、数据模型、接口和错误码规范实现领域逻辑与服务，编写单元和契约测试。不得未经批准改变数据库、公共接口、权限或审批语义。

主要 Skill：后端模块开发、领域建模、错误处理、事务实现、契约测试、并发与幂等处理、缺陷修复。

### 4.7 数据与接口工程师

负责数据库模型、迁移、API/事件契约、数据一致性、外部集成和接口兼容性，维护错误码登记表。对数据库和接口变更执行独立契约审查。

主要 Skill：数据建模、数据库迁移、API 设计、Schema 校验、接口兼容性、数据质量、外部集成和契约审查。

### 4.8 自动化测试工程师

从需求和设计独立建立测试策略、自动化用例、需求追踪和回归范围，验证正常、边界、错误和恢复路径。不得只根据已有实现反推测试，也不得以覆盖率数字代替行为验证。

主要 Skill：测试计划、单元/契约/集成/E2E 测试、测试数据、覆盖审计、回归测试、缺陷复现和发布验收。

### 4.9 集成发布与 SRE 工程师

负责构建、CI/CD、环境配置、集成、部署、灰度、监控、告警、回滚和运行手册。只接受通过前置门禁的版本，不在发布阶段静默修改业务实现。

主要 Skill：环境检查、构建发布、集成测试、数据库发布、可观测性、容量评估、灰度、回滚、故障响应和发布后验证。

## 5. 项目经理的复杂度与组队规则

项目经理对以下维度按 `0-3` 评分：业务规则、模块依赖、前端交互、数据与迁移、接口集成、权限审批、AI 不确定性、性能可靠性、测试回归、发布运维。总分用于估算规模，硬触发条件用于决定必须加入的岗位。

| 总分 | 项目等级 | 建议 Agent 实例 |
|---|---|---|
| 0-8 | 小型 | 6-9；允许岗位暂不激活，不允许作者自批 |
| 9-17 | 中型 | 9-14；前后端或模块可各增加实例 |
| 18-24 | 复杂 | 15-20；拆分模块、测试和发布工作流 |
| 25-30 | 高风险 | 20+；增加专项复核和人工批准 |

硬触发条件：

- 有用户界面：启用 UI/UX 与前端规范工程师、前端开发工程师。
- 有数据库或公共 API：启用数据与接口工程师。
- 有多角色权限或审批流：技术设计架构师负责设计，数据与接口工程师和独立审查实例共同复核。
- 有 AI 调用：任务必须包含结构化输出约束、离线评测和失败恢复；项目经理为相应开发或测试岗位分配 AI 专项 Skill。
- 有支付、删除、隐私或敏感数据：增加第二个独立审查实例，并保留人工批准。
- 有多环境、迁移或高可用要求：启用集成发布与 SRE 工程师并设置回滚门禁。
- 有三个以上相互独立模块：按依赖图增加开发 Agent，不让单一 Agent 负责整个项目。

## 6. 文档责任矩阵

`A` 为结果负责，`R` 为编写或执行，`C` 为参与审查，`I` 为知会。`A` 与 `R` 可以属于同一岗位，但不得是同一个 Agent 实例的唯一批准；必须从 `C` 中指定未参与编写的审查实例。项目经理只验证审查证据和职责分离是否成立，不替专业审查人作结论。

| 文档 | A | R | C |
|---|---|---|---|
| 项目需求文档 | 产品与需求工程师 | 产品与需求工程师 | 项目经理、架构师、测试工程师 |
| 架构设计文档 | 技术设计架构师 | 技术设计架构师 | 数据接口、前端规范、SRE、测试 |
| 前后端代码生成规范 | 技术设计架构师 | 前端规范、前后端开发 | 测试、数据接口 |
| 数据库和接口设计规范 | 数据与接口工程师 | 数据与接口工程师 | 架构师、后端、测试、SRE |
| 错误码规范 | 数据与接口工程师 | 数据接口、后端 | 前端、测试、SRE |
| 自动化测试规范 | 自动化测试工程师 | 自动化测试工程师 | 架构师、开发、SRE |
| 公共组件和方法清单 | 技术设计架构师 | 前端规范、前后端开发 | 数据接口、测试 |
| 审批和权限设计规定 | 技术设计架构师 | 架构师、数据接口 | 产品、后端、测试、SRE |
| 分模块详细设计 | 技术设计架构师 | 对应开发岗位 | 数据接口、测试、前端规范 |
| 功能开发详细设计 | 技术设计架构师 | 对应开发 Agent | 测试、相关接口责任人 |

## 7. 项目生命周期与门禁

### P0 立项与组队

项目经理建立目录和文档基线，评估复杂度，选择岗位、Agent 实例和 Skill，输出 WBS、依赖图、RACI、风险和门禁计划。

**G0 通过条件**：范围、约束、复杂度、参与人员、任务责任和第一阶段输入完整。

### P1 需求与验收

产品与需求工程师编写 PRD；测试工程师同步设计验收条件；架构师评估可行性。

**G1 通过条件**：需求可测试、范围明确、歧义已解决、每条需求具有追踪编号和验收标准。

### P2 架构与全局规范

架构师组织架构、非功能需求、模块、状态和权限设计；专业岗位完成前端、数据接口、错误码、测试及公共资产规范。

**G2 通过条件**：关键决策有 ADR，接口与数据边界稳定，风险和失败恢复明确，规范均为 `APPROVED`。

### P3 详细设计与开发计划

将需求拆成模块和功能设计，建立接口依赖、任务 DAG、开发顺序、测试范围和交接合同。

**G3 通过条件**：任务达到 Definition of Ready，开发 Agent 无需猜测业务规则、接口或验收方式。

### P4 Skill 准备

专业岗位把批准文档中的流程转为项目 Skill。Skill 必须记录权威文档路径和版本，包含前置条件、步骤、确定性检查、输出、停止条件和交接对象。

**G4 通过条件**：Skill 不复制或改写业务规则；规则仍以文档为准；关键检查可重复执行。

### P5 分模块开发

开发 Agent 在限定目录内实现功能和自动化测试。并行任务必须不存在共享写入边界或前置依赖。

**G5 通过条件**：代码、迁移、文档回写和单元/契约测试完整，任务证据可复现。

### P6 独立审查

由未参与同一实现的 Agent 调用模块功能审查、前端规范审查、数据库/API 审查、权限审批审查等 Skill。没有独立人员时，项目经理创建同岗位第二实例。

**G6 通过条件**：阻断问题清零，非阻断问题有明确处置，作者未批准自己的交付物。

### P7 集成、系统测试与回归

测试工程师执行完整测试矩阵；SRE 执行构建、环境、迁移、部署和回滚演练。

**G7 通过条件**：需求追踪闭环，关键路径、错误路径和回归通过，无静默失败，发布及回滚证据完整。

### P8 发布与运行

SRE 按计划发布并执行健康、业务、日志、指标和告警检查。项目经理汇总证据，人工批准高风险放行。

**G8 通过条件**：业务验收通过，监控生效，回滚可用，版本、文档和运行状态一致。

### P9 复盘与维护

缺陷和事故必须回溯到遗漏的需求、设计、规范、Skill、测试或门禁。先修正事实来源，再修正自动化和实现。

## 8. 任务与交接合同

每个任务至少包含：

```yaml
task_id: TASK-0001
objective: 可验证的一句话目标
owner_agent: 岗位和实例编号
reviewer_agent: 未参与实现的岗位和实例编号
tester_agent: 测试岗位和实例编号
required_skills: []
input_documents: []
allowed_paths: []
dependencies: []
acceptance_criteria: []
verification_commands: []
output_artifacts: []
risks: []
handoff_to: 下一责任人
```

任务状态统一为 `BACKLOG -> READY -> IN_PROGRESS -> REVIEW -> VERIFY -> DONE`，无法继续时标记 `BLOCKED` 并记录阻塞证据。缺少输入、审查人、验收标准或验证方式的任务不得进入 `READY`。

## 9. Skill 治理

### 9.1 Skill 最小结构

每个项目 Skill 必须明确：触发条件、责任岗位、权威文档、允许工具和目录、前置条件、步骤、完成标准、确定性检查、输出证据、停止条件、禁止事项和交接对象。

### 9.2 建议的项目 Skill

| 岗位 | 建议 Skill |
|---|---|
| 项目经理 | 项目初始化、复杂度评估、人员配置、计划拆解、任务分配、质量门禁、交接验证、变更影响分析 |
| 产品需求 | PRD 编写、用户故事、验收标准、需求追踪、需求审查 |
| 技术架构 | 架构设计、ADR、模块设计、功能设计审查、模块功能审查 |
| UI/UX前端规范 | 用户流程、设计系统、前端生成规范、前端规范审查、组件复用审查 |
| 前端开发 | 前端模块功能开发、组件测试、前端缺陷修复 |
| 后端开发 | 后端模块功能开发、错误处理、契约测试、后端缺陷修复 |
| 数据接口 | 数据建模、API设计、迁移执行、接口契约审查、错误码审查 |
| 自动化测试 | 测试计划、测试生成、覆盖审计、E2E、完整回归 |
| 集成发布SRE | 环境检查、构建发布、迁移门禁、灰度、回滚、发布后验证 |

Skill 不得静默修改它所引用的规范。发现缺失或冲突时必须停止并提交文档变更请求。

## 10. 完成定义

一个项目或阶段只有同时满足以下条件才能完成：

- 需求、架构、规范和实现之间可追踪。
- 所有必需文档处于批准或基线状态。
- 所有代码和配置均有独立审查。
- 正常、边界、错误和恢复路径均有测试或明确风险接受记录。
- 构建、部署、监控和回滚经过验证。
- 未解决问题、限制和延期项被显式记录。
- 交付证据足以让另一组 Agent 在无口头背景下继续维护。
